01 / 背景

60+ 个指标，
每天打开
等于没打开.

CONTEXT

2021 年底接手时，全行的网点经营看板是一张60+ 个指标 + 大量同比 / 环比 的密集表格。每天早 7:30 自动推到行长邮箱。看了半年，行长日活 31%，且打开后停留时间不到 40 秒。

调研下来真因不复杂："看板告诉我业绩在掉，没告诉我谁掉了、为什么掉、我该做什么。" 60 个指标互相之间没有逻辑顺序，每个指标都是一个独立数字。看完之后回不到行动。

立项的时候我提了一个朴素到几乎不像新观点的判断："看板的产品形态错了。它不该是表格，它该是工作流入口。" 这是我做 PM 至今所有工作的方法论起点。

立项前的真实声音
"我每天打开邮件看一眼数字，红的多就紧张，绿的多就开心。然后关掉。该开晨会还是开晨会。"
— 某网点行长 · 调研第 5 周
02 / 我做了什么

把 60 个指标
压成三段：
这事好不好、为什么、该怎么办.

APPROACH

三段式不是简单的「合并指标」。本质是把数据产品的工作从「展示」前推到「指导」。

第一段「健康度」回答"现在好不好"——把 60 个指标加权合成 1 个 0–100 分数，颜色化。第二段「异常归因」回答"为什么不好"——找出贡献最大的 3 个子指标。第三段「动作建议」回答"该做什么"——把归因结果接到具体的运营 SOP 上。

01
健康度
1 个 0–100 分
60+ 指标按业务权重合成。绿 / 黄 / 红三色。行长 5 秒内知道今天是好是坏。
02
归因
Top 3 贡献项
为什么是这个分。从子指标维度自动拆解，输出三条句子。不让行长自己看 60 个数字。
03
动作
SOP 库匹配
归因结果接运营 SOP 库。"建议本周内 召开理财营销动员会 / 排查近 7 日大额流失客户"。
↓
入口
点击进系统
每条动作建议都带一个"开始处理"按钮，跳进对应业务系统。这是把数据产品和工作流粘起来的关键。
03 / 关键决策

三个让看板
变成工作流的
决定

KEY DECISIONS
01.
健康度必须能讲故事
第一版健康度公式做得太复杂——27 个子指标加权。结果是行长不信任分数。V2 改成 9 个一线员工都能背的核心指标，权重和分行业务侧共定。"分数为什么是 72，能讲清楚"成了硬约束。
4.6 / 5 行长信任度（V1: 2.9）
02.
归因从规则升到算法
V1 的归因是 "哪个子指标同比下滑最多就报哪个"。粗暴。V2 用 SHAP 值做特征贡献度分解，能区分"季节性正常波动" vs "真实异常"。误报率从 38% 降到 12%。误报多了行长不再看，归因质量是看板信誉的命门。
38% → 12% 异常误报率
03.
动作建议接业务系统
这是看板从「读」变「做」的关键一步。我和运营条线对齐了 24 个标准 SOP，每个 SOP 都对应一个业务系统的入口。"建议处理大额流失客户"——点击直接跳进 CRM 的预筛清单。数据产品不接执行端，等于没做。
+38pct 异常处理及时率

这个项目对我个人最重要的产出是方法论本身：

—— 三段式（健康度 → 归因 → 动作）后来变成我做所有 toB 产品的默认结构；

—— 《数据产品设计规范 V1.0》被部门采纳，后续 3 个数据产品直接复用骨架；

—— "看板要是入口不是展示" 这一观点直接催生了 2023 的推荐项目（从被动看 → 主动跟）和 2024 的 RAG（从查信息 → 给答案）。

06 / 反思

回看的话，
三件事我会改

LESSONS
01
V1 的健康度公式太工程师，27 个指标看起来很科学，但行长就是不信。能讲明白 > 数学最优。这条经验后来反复救我，特别是在做 RAG 的引用展示和 Agent 的决策可解释时。
02
动作建议库本应该 V1 就做。V1 只做了健康度 + 归因，行长说"我知道哪里不好，然后呢"。我以为「然后呢」是下一期需求。现在回看，不接执行端的数据产品其实没上线，三段必须同时存在才有产品。
03
没有给分行行长定制权重。统一权重在全行推广时遇到强反对——一线分行和支行重心完全不同。后续补了「分行自定义权重」才平息。统一性是数据治理的，不是产品的。

WHAT'S NEXT

2022 的这个项目是我后面 3 年所有工作的方法论根。健康度 → 归因 → 动作变形为：

—— 2023 推荐项目的 分层 → 匹配 → 时机（也是三层）；

—— 2024 RAG 助理的 检索 → 引用 → 拒答（三步骨架）；

—— 2025 Agent 的 读 → 匹 → 动 → 傅（在三段上扩了"恢复"）。
