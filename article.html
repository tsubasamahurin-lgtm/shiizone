为什么我现在
不再写 PRD.

写了六年 PRD，发现真正决定一个 AI 产品好坏的，从来不是文档里写了什么——而是文档之外的那些 prompt、那些 eval、那些没法被排版的细节。

BY 王艺师 · YISHI WANG FILED IN OBSERVATION 深圳 · SHZ EST. READ — 12 MIN

上个月，团队里一个新来的工程师问我：「这个功能的 PRD 在哪儿？」

我愣了一下，意识到自己已经有大概八个月没认真写过一份 PRD 了。不是因为偷懒——这八个月里我的产出反而比之前任何一段时间都多。是因为我们做的东西——一个金融场景的 RAG 助理——它的「需求」根本不长在文档里。

它长在一份会随着模型升级而失效的 system prompt 里，长在一组每天跑一次的 eval 用例里，长在一线员工每周给我们标的 200 条「这个回答不对」的 case 里。这些东西，没有一样适合写进 Notion 的需求文档。

PRD 假设了一个已经消失的世界

传统 PRD 的核心假设是：需求是可以被一次性、完整地描述的，工程师拿到描述后会忠实地实现它。

这个假设在写一个登录页、一个支付流程、一个后台管理工具的时候都成立。需求空间是封闭的——你能枚举所有边界情况：密码错了怎样、卡过期了怎样、网络断了怎样。

AI 产品的需求空间是开放的。

AI 产品的「需求」不是写出来的，
是被发现的。

没有任何文档能枚举用户会问 GPT-4 的全部问题。所谓的「需求」只能在真实流量出现之后，通过反复地看用户的输入、看模型的输出、看哪里崩了，才能被定义出来。

这种工作方式更像是调音，不是装修。你不会先画一张图纸再让木匠按图施工。你会先让乐器响起来，然后一遍遍地拧——那根弦松了，那个键卡了，那段共鸣不对——直到声音对了。

那不写 PRD 写什么？

我现在大部分时间在写三种东西：

  • Eval set——一份小但精的测试用例，每次模型/prompt 变了都跑一次。它取代了 PRD 里「期望行为」那一栏。
  • Prompt + 注释——我们的 system prompt 现在是带版本控制的代码，每一段都有 // 这段为什么这么写 的注释。它取代了 PRD 里「业务规则」那一栏。
  • Loom 视频——给团队解释一个想法或者复现一个 bad case，30 秒视频比 3 页文档有效得多。它取代了大部分需要「对齐」的会议。

这三样东西的共同点：它们的更新成本极低，而且它们的「真实程度」远高于 PRD。 Eval 跑一次就知道效果，prompt 改完就生效，视频说什么就是什么。PRD 写完往往就和实现脱节了。

这不是「不要写文档」

看到这里你可能以为我在主张「文档没用」。恰恰相反。我比以前更依赖文档了——只是文档的形式变了。

好的文档应该和它描述的系统一起呼吸；坏的文档是给系统拍的死照片。 —— 我自己说的

一份 PRD 写完之后就停止更新，三个月后它和真实产品的对应关系约等于零。但一份 eval set 必须和产品同步，否则它就跑不通——这种「文档无法和现实脱节」的约束，恰恰是 AI 产品时代我想要的。

我现在的工作流大概长这样：

周一：看上周收集的 bad cases，从里面挑 10 条最有代表性的，加进 eval set。

周二到周四：调 prompt 或者改流程，让 eval 通过率从 78% 涨到 84%。中间和工程师 sync 三次，每次 15 分钟，用 Loom + 截图。

周五：上线 A/B，给销售/客服同学解释这次改了什么——一封 Slack 长信，不是 PRD。

// 当然，有些场景 PRD 还是必要的——比如要和另一个团队对接 API，比如做合规审计。
// 但日常的产品迭代，我已经基本不写了。

最后一句

这篇不是给所有 PM 看的——如果你做的是非 AI 产品，PRD 大概率仍然是对的工具。

但如果你正在做 AI 产品，并且还在每周交一份 PRD，可以问自己一个问题：

我的 PRD 里写的东西，
有几行能被 eval 验证？

如果答案是「很少」——那这份文档，可能就不是你产品最薄的那块墙。
