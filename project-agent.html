01 / 背景

RAG 解决了
「能查到」。
但查到不等于做完.

CONTEXT

一期 RAG 助理上线 6 个月后，我拉了 3 个试点分行的使用日志看。查询量增长了，员工反馈也齐，但业务结果指标不动。

跟三个柜员贴身观察一下午，问题才明白：查到「该推智能保」之后，员工还要在 4–6 个系统间跳转——查持仓、查额度、查双录资格、预约理财经理、发短信…… 「知道该做什么」只是起点。

立项时我拿这个去敲了事业部领导。被追问的问题是「为什么不接着加 RAG 内容」。我的回答：再多的知识也压缩不了动作时间。

调研现场原话
"我知道这客户适合什么。但到心算组 → 查资格 → 查额度 → 预约理财 → 发短信，走完一趟五分钟起。上个客户还在这个间隙里走了。"
— 某支行柜员 · 现场观察第 3 周
02 / 我做了什么

一个可被反悔的
Agent，不是一个
什么都能做的 Agent.

APPROACH

金融场景里「全自动」是个陷阱设计。员工不会用一个「他不知道刚刚发生了什么、他也反悔不了」的系统。所以三个设计原则从 day 1 就是：可解释、可反悔、可接管。

又所以我把工具粒度对齐到员工脚本里的动作，而不是后端 API 的划分，同时按「读 / 匹 / 动 / 傅」四个职能划分。这让模型选工具的准确率从 71% 提到 89%。

01
读 READ
3 个工具
客户持仓 / 近 90 天联系 / 家庭成员。只读不变更任何状态，默认走自动档。
02
匹 MATCH
3 个工具
产品推荐 + 与客户画像的适配理由。输出含凭据链路，供人工复查。
03
动 ACT
4 个工具
预约理财经理 / 发送短信 / 创建联系人务 / 发起双录。默认走确认档，中高风险强制人手点。
04
傅 RECOVER
2 个工具
失败重试 / 升级给人。上下文完整转交，不让员工补上下文是头号原则。
03 / 关键决策

三个让采纳率
真涨上去的
决定

KEY DECISIONS
01.
三档协作 · 自动 / 确认 / 接管
不是一个「全自动 vs 手动」的二选一。按「可逆性 × 风险估值」把每个工具预调到 3 个档位之一。查询走自动；资金动作默认走确认；合规敏感 / 大额强制接管。这是从一期 RAG「拒答机制」迭代出来的信任设计。
+12pct 员工信任度 · NPS 调研
02.
工具按心智划，不按 API 划
后端的客户模块有 14 个 API，但员工脑里只有 3 件事：这客户是谁、以前给他推过什么、最近聊什么。我把这 14 个 API 重包为 3 个工具，模型选对工具的准确率从 71% 跳到 89%。命名 / 描述 / 入参一齐对齐到一线话语。
+18pct 工具调用准确率
03.
8 维评测 · 传承 RAG 骨架
从 RAG 的 6 维评测拓到 8 维：+任务完成率、+工具调用准确率、+决策链路合理性、+端到端耗时。每次上线前跑 200 条场景样本。评测不仅是安全网，还是说服老板放量的唯一语言。
2 周 → 3 天 单次迭代验证周期

06 / 反思

回看的话，
三件事我会改

LESSONS
01
「自动档」放太早是 V2 初期最大的错。当时认为人机初期词输三档距离低代价上手比演低代价，让查询类工具默认走自动。但「工具选错」发生在查询类上同样严重——查错了客户。V3 推了 3 个月才调回。
02
工具命名第一版是工程师口吻：get_customer_position / fetch_holdings。员工看不懂。V2 改为「查持仓 / 看联系」后，接受度马上涨。命名不是现身外的事。
03
三档之间的「档位预测」还是人工设定，不是模型预测。下一代 Agent 应该让 LLM 自己根据场景、金额、客户画像预测该走哪档，而不是我提前刷档。
07 / 下一步

从「替我做」
到「知道何时不该做」

WHAT'S NEXT

现阶段重点是让档位预测自动化—— 让 LLM 根据上下文预测一个工具应走自动 / 确认 / 接管，不是被动受产品预设。评测体系也从「任务完成」升级为「信任度」：员工跳过确认 / 还是查看凭据 / 是否起疑提示。

金融场景里最难的不是「帮你做」，是「知道何时不该做」。下面有个对话窗口，想问工具设计、三档协作、评测体系，随便聊。
